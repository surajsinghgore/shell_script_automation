# The server — what lives where, and rebuilding it from nothing

Written against the box these scripts were built on. Yours will differ in
addresses; the shape won't.

---

## What it is

| | |
|---|---|
| OS | Ubuntu 26.04 LTS |
| Node | v22 (via NodeSource) |
| Process manager | pm2 7 |
| Web server | nginx |
| TLS | certbot / Let's Encrypt |
| RAM | 908 MB + 2 GB swapfile |
| Disk | 8 GB volume, ~6.7 GB usable |

Nothing here is installed by hand — `setup` puts it there, and skips anything
already present.

---

## The layout

```
/home/<user>/apps/<site>/              git checkout + node_modules
                                       (never served directly; the build happens here)

/var/www/<site>/releases/<ts>-<sha>/   one complete build
/var/www/<site>/current -> releases/…  the symlink that is actually live
/var/www/<site>/start.sh               pm2 wrapper: sets PORT, loads env   (node/next)
/var/www/<site>/ecosystem.config.cjs   pm2 config                          (node/next)
/var/www/<site>/.env.export            runtime vars, shell-quoted, chmod 600

/etc/nginx/sites-available/<site>      the server block
/etc/nginx/sites-enabled/<site>        symlink to the above
/var/log/nginx/<site>.access.log       per-site, so one app's traffic is readable
/var/log/nginx/<site>.error.log

/home/<user>/.git-credentials          the deploy token, chmod 600
/home/<user>/ops/healthcheck.sh        the cron health check
/var/log/healthcheck.log

/swapfile                              2 GB, needed for builds on a 1 GB box
```

**A release is immutable.** Deploys never edit a live directory — they build a
new one and move a symlink. That is what makes rollback a two-second operation.

---

## Who owns what

| Concern | Where it is decided |
|---|---|
| Which branch a site deploys | `<engine>.<env>.conf` **on your laptop** |
| The app's variables | `.env.<env>` **on your laptop**, uploaded at deploy |
| Which port a process listens on | the same conf, passed to pm2 as `PORT` |
| Which domain reaches which site | nginx `server_name`, generated from the conf |
| What restarts on reboot | pm2's saved process list (`pm2 save`) |

The server holds **no configuration you cannot regenerate** — except the TLS
certificates and the DNS records, neither of which lives here.

## Rebuilding from a blank Ubuntu box

This is the whole disaster-recovery procedure.

**1. Launch the instance.** Ubuntu LTS, and give it a bigger volume than you
think you need — 16 GB is the sensible floor if you plan to run Next.js. Attach
the same SSH key, or a new one and update `PEM_PATH` in each conf.

**2. Point DNS at the new IP.** Every A record for every site.

**3. Update the server address:**

```bash
cd react   # and next, and node
```

```bash
./react-develop.sh config main
```

Change `SERVER_HOST` to the new IP. Everything else is already correct.

**4. Deploy. That's it.**

```bash
./react-develop.sh setup all
```

Setup installs node, pm2, nginx, certbot and ufw, clones each repo, builds,
publishes, writes the nginx blocks and issues certificates. A site that took an
afternoon to set up the first time comes back in the time it takes to build.

**5. Restore the health check:**

```bash
./ops/install-healthcheck.sh --run
```

**6. Harden it:**

```bash
./react-develop.sh harden
```

fail2ban, unattended security upgrades, sshd lockdown, swap.

## What you would actually lose

| | Recoverable? |
|---|---|
| Application code | yes — it is in git |
| Build output | yes — rebuilt from source |
| nginx config | yes — regenerated by `setup` |
| pm2 config | yes — regenerated by `setup` |
| TLS certificates | yes, but re-issued — counts against Let's Encrypt's weekly limit |
| **Your `.conf` and `.env.*` files** | **only if your laptop still has them** |
| **Any database on the box** | **only if you have backups — these scripts do not make any** |

Those last two are the real exposure.

**Back up your configs.** They are gitignored for good reason — they hold a git
token — but that means they exist in exactly one place. Copy them somewhere
encrypted:

```bash
tar czf ~/vps-configs-$(date +%F).tar.gz */*.conf */.env.*
```

Keep that off the laptop it came from.

**These scripts do not back up databases.** If you add Postgres or MongoDB to
this box, that is a separate job and nothing here will do it for you.

## Capacity

Measured, per environment:

| Stack | Disk | RAM |
|---|---|---|
| React SPA | ~120 MB | none — no process runs |
| Node API | ~320 MB | ~150 MB |
| Next.js SSR | ~660 MB | ~250 MB |

Plus ~5 GB for the OS, node and the swapfile.

On an 8 GB volume that means **one Next.js app plus two or three static sites**.
A second Next.js environment does not fit, and the scripts refuse rather than
filling the disk — which matters, because a full disk on this box has already
broken `git` mid-command and left systemd units failing.

**Growing the volume**, when you hit that:

```bash
sudo growpart /dev/nvme0n1 1 && sudo resize2fs /dev/nvme0n1p1
```

Resize the EBS volume in the AWS console first. No downtime, no data loss. Run
`lsblk` if your device is named differently — older instances use `/dev/xvda`.

## Routine checks

```bash
./ops/install-healthcheck.sh --tail
```

```bash
./react-develop.sh status main
```

On the server:

```bash
journalctl -t healthcheck --since '1 day ago'
```

Watch for: disk above 85%, a climbing pm2 restart count (a crash loop), and
`systemctl --failed` — the first symptom of a disk that filled while you were
not looking is usually `logrotate` or `man-db` failing.

## Firewall and access

ufw allows 22, 80 and 443 only. SSH is key-only after `harden`.

To restrict SSH to your current IP — useful on a laptop that moves:

```bash
./react-develop.sh allow-ip
```

That needs `SG_ID` and `AWS_REGION` in the conf and the AWS CLI installed. It
rewrites one security-group rule and leaves any others alone.
